## IMMEDIATE NEXT TASK: E50 - the draft-reserve fix (user approved)

Goal: recover the fork's 1.7 t/s TG deficit (9.0 -> ~11+) by giving the
DFlash DRAFT context stock-like compute buffers. Should cost ZERO ctx:
at 250k the ledger has ROCm0 ~1290 MiB free post-drafter (journal E20
W3 tables); the fix needs ~600 MiB mostly on ROCm0.

Evidence chain (journals E41-E50):
- Base decode identical fork-vs-stock (6.9 = 6.9 t/s no-spec, same sha).
- Fork's spec machinery: draft phase = 23.0 s of a 115 s TG task
  (~43 ms/round, from the fork's own "dur(b,g,a)" stats line).
- Draft graph fragments into 23 scheduler splits in BOTH binaries; the
  fork executes those fragments ~4-8x slower. Prime suspect: the fork's
  frugal compute-buffer sizing (276 MiB target / 415 MiB draft vs
  stock's 1302/1021) creating buffer-reuse serialization.
- Exonerated: Vulkan fix/optimizer (AB5), fused-GDN forcing (AC1),
  checkpoints/cram (recover only 0.8 t/s, break prompt-restore:
  server-context.cpp:3436 gates it on n_ctx_checkpoints > 0 - never
  ship CKPT=0 for the chat backend), draft-device pinning (aborts, D15
  class), CPU drafter (helps shallow only, AD3).

Implementation pointers:

  ctx_other / draft ctx creation; params.draft). Its llama_context runs
  the fork's reserve machinery in src/llama-context.cpp sched_reserve()

  (~line 2460, graph_reserve) plus model.hparams.no_alloc.
- Surgical approach: exempt the DRAFT context from frugal sizing (e.g.
  a cparams flag set at draft-ctx creation that forces the

  If TG >= ~10.5, validate at c 250000 (headroom argument above), then
