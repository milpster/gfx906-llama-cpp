## Pipeline-parallel fix session (2026-08-27 night, D/T series)

User request: "fix pipeline parallel properly, use both our failure cases to
test" - G3 (UD+q8V prod shape: startup abort "failed to create MTP context")
and F7 (i1+f16: mid-PP "MUL_MAT failed / no kernel image").

Investigation trail (all evidence in bench/logs/lane-{D,T}*.log):
- D1: PP=on + HIP_GRAPH=0 runs the FULL protocol at parity -> "pipeline" runs
  are actually post-fallback non-pipeline runs (see below); also client hung
  on the final response in that run.
- D2: PP=on + HIP_LAUNCH_BLOCKING=1 crashes IDENTICALLY -> not async-error
  misattribution, not capture-only.
- Key log fact: every PP=on run (F7, D2, D4) shows exactly one 2026 MiB
  alloc failure + one "retrying without pipeline parallelism" -> the pipeline
  reserve (4x tensor copies, GGML_SCHED_MAX_COPIES=4) NEVER fit on this rig;
  pipeline was never actually active in any lane.
- The retry fallback was broken twice over: (a) it asked +117 MiB more on
  VK1 than a fresh start (backend pool debris from the failed attempt;
  destroying/recreating the sched does not reclaim it - T1 proved this with
  the destroy-first fix in place), which hard-aborts memory-tight configs
  (G3); (b) post-retry state corrupts later graph capture -> misreported
  "no kernel image" crash (F7/D2). D3/D4 showed the crash is timing-sensitive
  (an fprintf in mul_mat masked it) - i.e. a latent race we never pinned to
  a kernel, made unreachable instead.
- ggml-cuda's concurrency planner (concurrent_events / side streams) only
  activates with GGML_CUDA_GRAPH_OPT=1 AND exactly 1 CUDA device -> inert
  on this rig.

FIXES (src/llama-context.cpp + ggml-cuda.cu):
1. sched_reserve() restructured: the live scheduler is ALWAYS created
   non-pipeline and reserved first (the known-good path). Pipeline is only
   attempted afterwards, on a scratch scheduler, gated by a capacity check
   (per-device free >= 8x plain compute buffer, 8x measured from the 2026 vs
   236 MiB ratio), and adopted only on success. A failed attempt can no
   longer leave the context without working buffers or poison later capture.
2. ggml-cuda graph_compute: skip CUDA-graph capture when the stream context
   has concurrent regions (pipeline side streams); hygiene for single-GPU
   rigs where the planner can run.

Tests on the fixed build (both user failure cases):
- T4 (= G3 case): "pipeline parallelism disabled: device Vulkan1 has 575 MiB
  free, needs an estimated 1965 MiB" + buffers byte-identical to a pristine
  production startup (239.89/245.65/239.89) + LISTENS. No retry path taken.
- T5 (= F7 case): full protocol completes, zero errors: PP 331.5, fill 103612
  @ 217.8, TG@120k 9.5, acc .689, sha 694720d04453 = byte-identical to the
  F3/F5/F8 champion runs.
- T6 regression: champion config (no PP) listens, buffers healthy.

Verdict: --pipeline-parallel is now SAFE on this rig (clean, logged
degradation when it cannot fit - which is always, given the 4x copy-buffer
cost) and remains pointless at -np 1 (D1 parity + 3x historical no-gain).
Debug instrumentation (mul_mat dispatch dump) added during D3/D4 and removed
afterwards; builds verified clean.
