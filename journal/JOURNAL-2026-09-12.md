## E167 — upstream #27841 (GCN MMQ config) applicability to prod

Task: does prod benefit from ggml-org/llama.cpp PR #27841 ("ggml-cuda: hip: add
missing AMD GCN MMQ config", thelittlefireman, merged 2026-09-12, merge c8edceb0)?

### What the PR is
Adds per-quant tuned GCN (wave64) MMQ tile table `mmq-config-gcn.cuh` + routes
gfx906/GCN to it in mmq.cuh. Key traits vs our table: nthreads 256 AND 512,
occupancy 2, I=64 or 128, J up to 128 (rdna2 caps 64), avoid MMQ fallback for
I<128, safeguard J<=64 for MoE and -sm tensor. PR self-reports big gains
(Q2_K +395%, Q8_0 +46%, Q4_1 +44%, Q6_K +34.5% avg) — but those are vs upstream
master's RDNA2-fallback tiles, NOT vs our tuned table.

### Findings (evidence)
1. Our fork ALREADY carries the #27841 Q6_K row. Commit cd97aeae0
   "mmq: vega Q6_K I=64/occ2 variant (upstream #27841 GCN row)".
2. Current HEAD mmq-config-vega.cuh = 220 uniform (256,1,128) rows + 11 Q6_K
   rows at (256,2,64). README (build-vega20-prod-verified) already credits
   "#27841's GCN row ... Q6_K I=64, occupancy 1->2, +20% PP".
3. PR gcn.cuh Q6_K rows are BYTE-IDENTICAL to our existing Q6_K rows
   ((256,2,64) x11, layout Q6_K). => main Q6_K model gets NO new tile delta.
4. prod main model = Qwen3.8-27B.i1-Q6_K.gguf (pure Q6_K, 21.4GB).
   prod draft = Qwen3.8-27B-DFlash2-Q4_K_M.gguf (Q4_K_M, 1.1GB).
5. Only delta = non-Q6K quants: our uniform (256,1,128) vs PR per-quant
   (256,2,64/128). In prod this matters mostly for the Q4_K_M draft
   (decode-only, small fraction of the work). Main-model PP lane should be
   ~parity.

### Verdict
Expected prod benefit: SMALL, likely within noise. Headline #27841 gains do NOT
transfer (measured vs upstream's worse baseline). The one real candidate is the
Q4_K draft path. Not worth adopting wholesale on PR self-reports; confirm with A/B.
