- E84 PP REGRESSION - the reason the ~10% PP loss happened and was fixed:
  production PP16384 fell from the 393/395 class (launchers on the
  Aug-28 build) to the 350 class after moving to novega builds.
  Two independent causes, found in sequence:
  1. LD_LIBRARY_PATH shadowing (E70, launcher fix): launchers set
     LD_LIB to build-dflash/bin (stale build); llama-server links via
     RUNPATH so the stale .so set silently shadowed the new binary
     end-to-end. Fixed to build-dflash-novega/bin. Alone this did not
     restore 393.
  2. Tuned-out kernels (the real ~10% loss). The Aug-28 build
     (source 5d317d32c) compiled the gfx906 vega-tuned MMQ tiles and
     tiled top-k UNGATED - active by default. The VEGA_TUNE gate
     commit 68f24f402 wrapped them behind GGML_CUDA_VEGA_TUNE_* flags,
     and the E50-V2 isolation build configured MMQ/TOPK/GRAPHS OFF to
     isolate a selector crash. That off-state was never A/B'd back:
     every novega-derived build since lost exactly the GEMM path that
     PP16384 is compute-bound on (perf-matrix 08-10). Verdict matrix
     pp394 (same model/split/ctx/drafter, only the binary differs;
     all repro True, canonical sha e54019ff6b42):
       old build        pp 362.2  fill 311.4  tg 12.10
       novega untuned   pp 324.6  fill 290.8  tg 13.70
       tunes restored   pp 371.1  fill 328.8  tg 13.40
     Tunes recover ~11% PP/fill AND stack with the selector + small-Q
     geometry work (TG stays at the new-build level, sha unchanged -
     the tuned tiles do not move greedy numerics).
  Adoption closed E83: release dir rebuilt tunes-ON, confirmed pp
  369.0 / fill 327.3 / tg 13.30 (lane scale); build-dflash-novega.sh
  now defaults MMQ/TOPK/GRAPHS=ON.
  Client-scale note: 393-class figures are the server pure-eval print;
