## mmap+mlock OOM (2026-09-25 22:26) - cause

Kernel killed llama-cli with file-rss 55.3 GB, system mlocked 55.0 GB. The loader's
final "CPU_Mapped 27465.95 MiB" line is the lazy mapping, not total host residency;
the separate 52.95 GiB ordinary mapping was fully locked. grow_to() locks a contiguous
prefix from the mapping base, so mmap+mlock on a partially-offloaded model also locks
every GPU-resident tensor's file pages.

## Selective mlock implementation

- llama_mlock::lock_ranges(): page-round, sort, coalesce, lock ascending; gap-tracked
  accounting; failed range stops cleanly.
- llama_model_loader: non-lazy mapped CPU tensor ranges collected per mapping and
  flushed once at load completion; full-file WILLNEED prefetch skipped when mlock is
  on (prefetch pollutes the cache the lock pass needs).
- raw_lock() uses mlock2(MLOCK_ONFAULT) on Linux: bulk populate was driving a page
  migration storm (vmstat: 57.9M migrations, ~221 GB copied, 16k compact stalls,
  loader thread D-state in __mm_populate). Lock-on-fault removes __mm_populate
  entirely; pages pin as PP first-touches them.

## PP steady-state bottleneck attribution (bench/logs/q38speed/bottleneck-pp/)

Steady state 18.4-21.0 t/s (warm server, selective mlock on, 43.09 GiB locked).
Sampler during pass: CPU ~0.4 cores (scheduler thread only, workers 0 ticks),
rocm-smi GPU use ~0%, VRAM 91-97%. Wall 22.8 s for a 460-token ubatch.

GGML_SCHED_SPLIT_TIMING=1 (splittiming/): inputs=21465 ms (93% of wall),
graph=1382 ms (6%), presync/ev ~0. 119 splits; ROCm0 carries 106 splits with
21218 ms of input phase (~200 ms/split; E147.3 measured 92 ms/split before the
n27 placement). CPU splits: 0 ms compute - CPU expert matmuls are noise.

GGML_SCHED_COPY_PHASES=1 (copyphases/): the input phase is expert staging:
EXPCOPY ids_sync ~0.4 s, issue 13-42 s, bytes 45.7 GB per pass at 1.09-3.44 GB/s.
Qwen3.8 routes near-uniformly (#28545: 98.6% of slots active in ~1.3k tokens),
so a 460-token ubatch touches ~all 512 experts of each CPU-hosted MoE layer and
the scheduler stages essentially the full CPU expert set through the pinned ring
every pass - pageable->pinned memcpy, single-threaded, at DDR-copy speeds.

Chain: near-uniform routing -> full expert set selected per pass -> 45.7 GB
staged at 1-3.4 GB/s -> 93% of PP wall. Explains the linear PP gains from every
ncmoe/projection promotion (less staged bytes) and idle CPU+GPU.

Fix directions, ranked:
1. Skip ring staging for host-resident locked experts: with selective mlock the
   expert pages are already pinned in RAM - compute can read them directly and
   the ring copy is pure overhead (bridges the mlock work to this bottleneck).
2. Multi-thread the ring issue path if staging must stay.
3. GGML_MOE_FULLCOPY_TOKENS semantics worth checking (routed-vs-full copy control).

Tooling: bench/pp-sampler.sh (thread utime + rocm-smi sampler during a pass).

## PP5712 experiments: PCIe x4 is the wall; experts-on-CPU is the escape (WIP)

Facts: both Radeon VIIs are PCIe gen3 x4. Microbench (bench/bench-h2d-reg.cu):
H2D is 1.36-1.70 GB/s for pageable, mlock, hipHostRegister AND hipHostMalloc -
the link, not pinning, is the limit. amdgpu rejects big hipHostRegister anyway
(dmesg "SVM mapping failed, exceeds resident system memory limit", no module
knob on this kernel), and hipHostRegister of 43 GB wedges in svm_range_set_attr.
Registration direction dead on this box.

PP512-scale baseline with staging: 17-21 t/s, 93% of wall = 45.7 GB/pass expert
staging through ROCm0's x4 link. Without the MTP draft sidecar (its fattn pool
OOMs the tight tenancy at >5k-token ubatches - ggml_cuda_pool_leg abort):
- GGML_OP_OFFLOAD_MIN_BATCH=999999 (all host-op pulls off, half the model lands
  on CPU): PP5712 51.2 first-touch / 64.4 warm t/s, TG collapses to 1.78 t/s.
  ROCm1 idle, vk1 idle: placement degenerate but DDR-fed CPU MMQ beats x4 staging.
- offload_op rejecting host-weight MUL_MAT_ID only: PP5712 79.5 t/s on pass 1
  (3.8x staged baseline), then GPU node-1 memory-access fault on pass 2 - some
  ROCm1 node dereferences an uncopied host input once the staging path is off.
  Reverted; the scheduler needs explicit input copies for CPU-placed MUL_MAT_ID
  before this mode is shippable. That is the remaining work with the biggest
  payoff (upper bound: ~10.9 s CPU compute + ~3 s transfers per 5132-token pass).
Tenancy in experts-on-CPU mode drops (r1 11/16 used): staging buffers and the
reserve shrink; the freed VRAM is headroom to re-promote resident experts.

## vk1 expert streaming probe (user idea): plumbing works, copy path is the wall

GGML_MOE_VK_STREAM_MIN_BATCH in the vulkan offload_op mirrors the cuda gate:
at prefill batches vk1 ACCEPTS the host-weight MUL_MAT_ID nodes that r0/r1
reject, so the fork's routed-expert staging (E147.6 grouped path) streams all
CPU experts over the 3080's x16 instead of computing on CPU. Sched confirmed:
backend order r0,vk1,r1 - first acceptor wins (ggml-backend.cpp ~970).

Results (PP5132, PP-on lane, draft live): pageable copies 136.2 t/s with
Vulkan1 split inputs = 70.9 s across 2 passes (~1.5 GB/s effective, 132 big
staging splits - the stream IS flowing); GGML_EXPS_RING=1 122.6 (the ring is
HIP-tuned; on vulkan it serializes worse). CPU compute mode remains best at
141 (PP-off). The x16 is only 12% utilized: vulkan tensor_set goes through
the host-mapped BAR, not a staging-buffer DMA pipeline like HIP's async set.

Next lever (big): a vulkan-side async tensor_set (staging buffer + queue
submit + event, like the HIP path the ring drives). At 10-12 GB/s the 45.7 GB
pass stream becomes ~4-6 s overlappable -> 250-400 t/s class. Also queued:
threads 11/15 sweep on the CPU mode; #29182 (vulkan MoE tiles) complements.
Numerics note: vk-stream changes accumulation order (vulkan MMQ) - sha gate
required before any promotion; CPU-mode lane unaffected.

## vk-stream arc: the "CPU mode" was vk1 streaming all along; two taxes found

Profiling revelation: the cpumoe-fix 148.5 t/s run has Vulkan1 inputs=118.6 s
(536 splits) - vulkan's DEFAULT offload rule accepts host-weight MUL_MAT_ID at
PP batches (cuda rejects via the gate), so every "gated CPU mode" run was
already streaming the routed experts to the 3080 over x16. The GGML_MOE_VK_
STREAM_MIN_BATCH gate changed nothing; EXPS_RING hurt (122 vs 136/148) via
per-copy presyncs; GGML_VK_STREAM_NO_PRESYNC + GGML_MOE_FULLCOPY_TOKENS both
neutral. Expert compute on vk1 itself: 0.18 s/pass (graph time) - the mmid
math is free; ALL cost is the copy path (~16.3 GB/pass, measured input time
~30-35 s/pass = ~3x raw copy, split-boundary event waits).

Also found: a 4-node CPU split of 10.7 s ONCE PER REQUEST in every config
(NOT the draft catch-up - it survived -devd rocm1 + DRAFT_UBATCH 128; NOT the
adaptive PLE planner - dropping --spec-type draft-mtp-adaptive for plain
draft-mtp left PP identical 135.5/137.3). Unknown; ~2 ms/token; the biggest
single remaining target together with the vk1 copy overhead.

Ported upstream #29182 (vk mul_mat_id pipeline guess from rows-per-expert
instead of total rows) - correct shape fix for our 80-rows/expert workload.

Draft completion stack (devd rocm1 + otd r1 + output.weight=r1 + DRAFT_UBATCH
128 + 40/42 CPU'd for fit): PP 134-137, TG 8.90 (adaptive). Plain draft-mtp
(non-adaptive): PP same, TG 2.42 - the adaptive controller is load-bearing
for TG; keep adaptive.

Numbers table (PP5132 warm): cpu-labeled/streaming 148.5 (orig override) /
141 (PP-off) / 137 (draft-r1, +2 CPU groups) / 136-122 vk-gate probes.
PP16384 on the shipped lane: ~134 mid-pass (canceled), clean number pending.

## THE 10.7 s mystery split: PLE table page faults. Fixed by -lzm on-direct. PP 185.5

Attribution (split-ops + shapes print in ggml-backend.cpp, gated on
GGML_SCHED_SPLIT_TIMING): the once-per-request 4-node CPU split is
GET_ROWS(2560x5132) + GET_ROWS(160x82112) + RESHAPE x2 = the qwen4exp PLE
input path (per_layer_tok_embd gather, 16 heads x 5132 tokens, plus token
embd gather). PLE = per-layer embedding, not prompt lookup.

Root cause: per_layer_tok_embd is a 27.46 GiB lazy mmap tensor. 43.09 GiB
locked + 27.5 GiB lazy > 62 GB RAM, so the table pages get evicted between
passes; the serial single-threaded graph GET_ROWS re-faults them at ~200 us
per row from NVMe. Measured 51,635 major faults per PP5132 pass (= the 11 s).

Fix: --lazy-mode on-direct (fork llama_lazy_reader, pread-based, rows sorted
+ deduped, 32 read workers, POSIX_FADV_RANDOM). The gather moves to
set_input() host-side and the graph consumes a staged F32 tensor.

Results (draft-r1-complete stack: devd rocm1, DRAFT_UBATCH 128, 40/42 CPU
groups, adaptive MTP, PP-on):
- -lzm on      : PP5132 134.1 / 137.2, TG 8.90, 51,635 faults/pass
- -lzm on-direct: PP5132 183.3 / 185.5 (+35%), TG 9.10, 187 faults/pass
- temp-0 sha warm-vs-warm: MATCH (cbecd32a...). First request after load
  differs from warm on BOTH configs (known lazy-init shape artifact).

Previous best was 148.5 (no-draft). New lane best: 185.5 with draft+TG 9.1.
