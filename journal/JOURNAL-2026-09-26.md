## mmap+mlock OOM (2026-09-25 22:26) - cause

Kernel killed llama-cli with file-rss 55.3 GB, system mlocked 55.0 GB. The loader's
final "CPU_Mapped 27465.95 MiB" line is the lazy mapping, not total host residency;
the separate 52.95 GiB ordinary mapping was fully locked. grow_to() locks a contiguous
prefix from the mapping base, so mmap+mlock on a partially-offloaded model also locks
every GPU-resident tensor's file pages.

## Selective mlock implementation

- llama_mlock::lock_ranges(): page-round, sort, coalesce, lock ascending; gap-tracked
  accounting; failed range stops cleanly.
- llama_model_loader: non-lazy mapped CPU tensor ranges collected per mapping and
  flushed once at load completion; full-file WILLNEED prefetch skipped when mlock is
  on (prefetch pollutes the cache the lock pass needs).
- raw_lock() uses mlock2(MLOCK_ONFAULT) on Linux: bulk populate was driving a page
  migration storm (vmstat: 57.9M migrations, ~221 GB copied, 16k compact stalls,
  loader thread D-state in __mm_populate). Lock-on-fault removes __mm_populate
  entirely; pages pin as PP first-touches them.

## PP steady-state bottleneck attribution (bench/logs/q38speed/bottleneck-pp/)

Steady state 18.4-21.0 t/s (warm server, selective mlock on, 43.09 GiB locked).
Sampler during pass: CPU ~0.4 cores (scheduler thread only, workers 0 ticks),
rocm-smi GPU use ~0%, VRAM 91-97%. Wall 22.8 s for a 460-token ubatch.

GGML_SCHED_SPLIT_TIMING=1 (splittiming/): inputs=21465 ms (93% of wall),
graph=1382 ms (6%), presync/ev ~0. 119 splits; ROCm0 carries 106 splits with
21218 ms of input phase (~200 ms/split; E147.3 measured 92 ms/split before the
n27 placement). CPU splits: 0 ms compute - CPU expert matmuls are noise.

GGML_SCHED_COPY_PHASES=1 (copyphases/): the input phase is expert staging:
EXPCOPY ids_sync ~0.4 s, issue 13-42 s, bytes 45.7 GB per pass at 1.09-3.44 GB/s.
Qwen3.8 routes near-uniformly (#28545: 98.6% of slots active in ~1.3k tokens),
so a 460-token ubatch touches ~all 512 experts of each CPU-hosted MoE layer and
the scheduler stages essentially the full CPU expert set through the pinned ring
every pass - pageable->pinned memcpy, single-threaded, at DDR-copy speeds.

Chain: near-uniform routing -> full expert set selected per pass -> 45.7 GB
staged at 1-3.4 GB/s -> 93% of PP wall. Explains the linear PP gains from every
ncmoe/projection promotion (less staged bytes) and idle CPU+GPU.

Fix directions, ranked:
1. Skip ring staging for host-resident locked experts: with selective mlock the
   expert pages are already pinned in RAM - compute can read them directly and
   the ring copy is pure overhead (bridges the mlock work to this bottleneck).
2. Multi-thread the ring issue path if staging must stay.
3. GGML_MOE_FULLCOPY_TOKENS semantics worth checking (routed-vs-full copy control).

Tooling: bench/pp-sampler.sh (thread utime + rocm-smi sampler during a pass).

## THE 10.7 s mystery split: PLE table page faults. Fixed by -lzm on-direct. PP 185.5

Attribution (split-ops + shapes print in ggml-backend.cpp, gated on
GGML_SCHED_SPLIT_TIMING): the once-per-request 4-node CPU split is
GET_ROWS(2560x5132) + GET_ROWS(160x82112) + RESHAPE x2 = the qwen4exp PLE
input path (per_layer_tok_embd gather, 16 heads x 5132 tokens, plus token
embd gather). PLE = per-layer embedding, not prompt lookup.

Root cause: per_layer_tok_embd is a 27.46 GiB lazy mmap tensor. 43.09 GiB
locked + 27.5 GiB lazy > 62 GB RAM, so the table pages get evicted between
passes; the serial single-threaded graph GET_ROWS re-faults them at ~200 us
per row from NVMe. Measured 51,635 major faults per PP5132 pass (= the 11 s).

Fix: --lazy-mode on-direct (fork llama_lazy_reader, pread-based, rows sorted
+ deduped, 32 read workers, POSIX_FADV_RANDOM). The gather moves to
set_input() host-side and the graph consumes a staged F32 tensor.

Results (draft-r1-complete stack: devd rocm1, DRAFT_UBATCH 128, 40/42 CPU
groups, adaptive MTP, PP-on):
- -lzm on      : PP5132 134.1 / 137.2, TG 8.90, 51,635 faults/pass
- -lzm on-direct: PP5132 183.3 / 185.5 (+35%), TG 9.10, 187 faults/pass
- temp-0 sha warm-vs-warm: MATCH (cbecd32a...). First request after load
  differs from warm on BOTH configs (known lazy-init shape artifact).

Previous best was 148.5 (no-draft). New lane best: 185.5 with draft+TG 9.1.

## Spec ckpt eviction: full-mode on-device TG without the PP cost. Promoted

Root cause of the -19% PP-after-TG: llama_io_write_device's dtor allocates
the checkpoint copies via ggml_backend_alloc_ctx_tensors_from_buft into
ctx->mem_storage[seq_id] - persistent device buffers with no free-at-will
API upstream ("getting the state ... invalidates all prior states" is the
only lifecycle rule). They squeeze the tight fit until context death.

Fix: new llama_state_seq_evict(ctx, seq_id) (mem_storage.erase) + server
hook at slot task start: evict tgt+dft ckpts and clear spec_ckpt when the
incoming prompt is >= GGML_SPEC_CKPT_EVICT_TOKENS (default 1024). Small
tasks keep checkpoints (no device alloc churn per TG round); the round
loop rebuilds at prompt end, so no load ever sees evicted storage.

First attempt evicted every task: PP1 244.6 but TG steady slipped to 10.3
and PP2 wobbled (217) - device alloc churn per round. Threshold variant:

## 2026-09-27 ~13:0x: MUL_MAT_ID regime analysis - campaign ledger closed

- PP regime: closed at silicon. Tile sweep already has 96.9% of MMQ cycles in
  the optimal tile config (J=64 fb=0), dp4a issue ~41% - instruction/memory
  bound. Only remaining PP lever is the quant mix (per-byte MMQ cost), which
  is excluded by the no-requant rule.
- Decode regime: batch-1 MUL_MAT_ID reads only the ROUTED expert slices
  (~21 MB/layer of the 1.36 GiB stack), so the existing tile-shaped MMQ
  handles the 4 VRAM-resident layers fine (0.02-0.6 ms/split graph times).
  The 48-slot cache arm's 4x regression was the cache machinery (insert
  traffic ~182 MB/step + hit/miss mixing), not raw batch-1 MMQ.
- A dedicated mul_mat_vec_q-style GEMV specialization for MUL_MAT_ID would
  be worth only ~1-3 ms/step on layers that are not the bottleneck.
- Structural walls, not kernel walls: 61 GiB experts > ~34 GB usable VRAM
  (capacity), PCIe 6 GB/s makes per-token device streaming ~115 ms (link),
  91 GiB > 62 GB RAM (no full residency anywhere).
- Final bottleneck stack (default lane, ~92 ms/token): ~40 ms per-layer
  round-trip syncs + ~36 ms RAM expert streaming + ~15 ms serialized
  staging receipts. The two designed-but-unbuilt surgeries remain the only
  path past it: cross-stream/event copies (hide the wait) and expert
  prefetch pipelining (hide the stream). Ceiling if both land: ~16-18 t/s.
