## QSA sparse FA: reserve regression root-caused, 200k ctx fits at ub5696

- Symptom: indexed path saved 1.44 GiB at 20k ctx but cost +761 MiB at 60k
  (dense 15389.87 vs indexed 16151.02 MiB total compute reserve).
- 20k placement-matched snapshots (NCMOE=28 TS=75,1,24, q8_0/q4_0):
  dense 8291.18, indexed 7917.12 -> -374 MiB. The regression scales with
  context, it is not a backend-placement effect.
- GGML_SCHED_DEBUG dump at the same placement: no indexer_top_k input
  crosses a split anywhere; QSA layers sit whole on their ROCm devices.
  The earlier "Vulkan rejects indexed FA, forces cross-device copies"
  hypothesis is dead for this lane.
- Peak-allocation traces via temporary GGML_ALLOCATOR_DEBUG (enabled in
  ggml-alloc.c, captured, removed, build-rcfix rebuilt clean):
  - dense host peak 1169.33 MiB: attn_inp_kq_mask 667.50 MB F16 + its
    view + leaf_117 visibility column 333.75 MB.
  - indexed host peak 1503.10 MiB: leaf_118 full bias 1335.00 MB F32;
    ROCm1 peak 7098.96 MiB with two live leaf_118 views plus a 1335 MB
    temporary alive at once.
- Root cause: LLAMA_QSA_SPARSE_FA rides the LLAMA_KQ_MASK_GEN input form,
  but build_qsa_top_k only accepted the dense mask as a valid causal mask
  for blk_bias selection. Under the generated form it silently fell back
  to the full [n_kv, n_tps, n_stream] F32 bias - n_kv*n_tokens*4 bytes
  per QSA ratio input, pinned for the whole graph.
- Fix (src/models/qwen4exp.cpp, build_qsa_top_k): a validated
  mask_col/mask_nvis pair now also selects blk_bias. Per-block bias
  (1/ratio of the cells) restored, per-cell causal mask generated
  in-graph by the existing build_kq_mask_rows path.
- 60k gate after fix: indexed total 10812.02 vs dense 15389.87 MiB
  (-4577.85 MiB, ~30%). Host 502.09 MiB (was 1503.10). Deterministic
  8-token completion byte-identical to the pre-fix sparse smoke.
- 200k unchunked attempt: exact blocker measured - ROCm0 cudaMalloc of
  11645906048 bytes fails. The n_kv*ubatch indexer-score family is the
  remaining oversize lifetime.
- 200k with the existing LLAMA_QSA_CHUNK=1024 knob (chunks the top_k
  score chain along the token axis): healthy slot n_ctx=204800, compute
  reserve ROCm0 3810.31 / Vulkan1 1785.00 / ROCm1 4979.68 / host
  1283.03 MiB, PP nodes 9363 (vs 7023 unchunked). Same deterministic
  8-token completion; TG 8.9 t/s.
- Working 200k lane: LLAMA_QSA_SPARSE_FA=1 LLAMA_QSA_CHUNK=1024 NCMOE=28
  TS=75,1,24 CTX=204800 CTK=q8_0 CTV=q4_0 UB=5696 SPEC=none PPFLAG=off
  ./run-qwen38f-fast.sh
- Incident note: one full ab-bench warm lane (33k-token double client run)

## 200k tenancy probes: all negative; PP per-token cost exposed

- User reverted the freeze-protection sysctls (page-cluster 3,
  watermark_scale_factor 10, min_free_kbytes 262144): the stutter was
  reclaim churn + no swap readahead, and the pre-fix host tensors that
  justified them are gone.
- GPU state during the 200k lane: ROCm0/1 ~14.3/16, Vulkan1 3.2/8 GiB.
  The free vk1 VRAM looks stranded but is NOT usable:
  - -ot expert overrides to Vulkan1/ROCm0/ROCm1 (T2: blk.26/27->vk1,
    NCMOE=26; T4: 5 layers across all three, NCMOE=23): buffers move
    exactly, splits drop 169->157, n_ctx=204800 holds - but TG collapses
    8.9 -> 0.07-0.19 t/s and prompt 1.41 -> 0.11-0.37 t/s. Outputs stay
    byte-identical. The fenced staging ring round-trips device-resident
    experts through fences per token; only ROCm_Host experts take the
    fast lane. NCMOE below 28 without an override is equally poisoned
    (the freed layers land on device buffers).
  - LLAMA_KQ_MASK_GEN=2 (direct-nvis for dense layers): same collapse
    (0.33/0.18 t/s). Mask fast path = the committed mode only.
- 200k PP reality: TG 8.9 t/s, but the first 5696-token ubatch did not
  complete in ~7 min (cold, with expert first-touch pushing MemAvailable
  12.3 -> 9.7 GiB; watchdog killed it). Per-token QSA chain cost ~0.11 s
  does not amortize across the ubatch the way the 20k lane does
  (115 t/s indexed there = 8.7 ms/token). Escape hatches walled:
  unchunked needs 11.1 GiB ROCm0 compute (fails), chunk 2048 exceeds
  ROCm0 by the same math, mode-2 masks and device experts are slow.
- Next lever if 200k PP must become usable: profile one warm ubatch

## 200k PP stall is a deadlock, not slowness

- Reproduced under observation: 200k lane, chunk 1024/1408, first
  full-width (5696-token) PP ubatch -> both Radeons 0% use with VRAM
  loaded, all server threads in futex except one in
  wchan=kfd_wait_on_events. Host waits on a KFD completion event that
  never signals; no GPU work pending. 4-token requests (single QSA
  chunk) and TG (8.9-11.0 t/s) run fine on the same server.
- Chunk 1408 fits and smokes byte-identical with best TG (10.98 t/s),
  but the full-width ubatch deadlocks identically -> chunk size is not
  the trigger; full-width PP is.
- Not HIP graph capture (no hipGraph use in tree). Suspects ranked:
  staging-ring fence signal loss at PP width, or a size-dependent
  32-bit offset in a KV-stride-indexing kernel (200k-cell cache views).
- Planned discriminators for next session (unexecuted): 60k ctx +
  5696-token probe (same runtime shapes, smaller strides) vs 200k +
  1024-token single-chunk probe; then gdb backtrace with
  ptrace_scope relaxed.
- Evidence: bench/logs/eqsfa-200k-chunk{1024,1408}-*.log,
  eqsfa-200k-chunk1024-stall-diag{,2}.log, per-thread wchan capture
  inside diag2 run.

## 200k PP stall root-caused to split-copier D2H hang

- ptrace_scope relaxed by user; live-client repro (setsid python
  holding the request open) + gdb thread apply all bt.
- Earlier "kfd_wait_on_events" capture was an artifact: probe used a
  python daemon thread that died on interpreter exit, so the server
  was idle, not stalled. HSA waiter thread is its normal standing
  state, not evidence.
- Real capture (bench/logs/eqsfa-200k-stall-gdb2.txt): main thread
  blocked inside ggml_backend_sched_compute_splits ->
  ggml_backend_tensor_copy -> ggml_backend_cuda_buffer_get_tensor ->
  libamdhip64/libhsa wait. Synchronous D2H read of a split input
  from a ROCm buffer never completes; GPUs 0%. All other threads
  futex-idle; CPU graph workers never launched (barrier wait).
- Implication: hang is in the 169-split graph's input-copy phase,
  BEFORE any compute. Explains insensitivity to chunk size, mask
  mode, expert placement. Not slowness - the copy waits on a
  queue/event that never proceeds.
- Next: repro + gdb thread 1 frame 12, dump registers (tensor ptr in
  rsi, size in rcx) and read tensor->name via x/s to identify the
  exact stuck tensor and copy size; then fix its placement or copy
  path. Candidate inputs: generated kq_mask / QSA bias / split
  boundary views sized by the 200k-long cache.

  src=CPU dst=ROCm0. Copy never returns; input 13 never reached.
- Split 7's input list at 5696 tokens: inp_pos, attn_inp_k_rot
  (262144 B), attn_inp_v_rot, k_idxs/v_idxs, leaf_112/114/118, two
  attn_inp_kq_mask entries (1024 B each, one VIEW) - a QSA attention
  split region consuming the generated-mask family.
- gdb2 + trace agree: hang is inside ggml_backend_tensor_copy for
  this small view (via cuda_buffer_get_tensor -> HSA wait). A 1 KiB
  copy blocking forever = dependency/event wedge on the copy path,
  not bandwidth.
