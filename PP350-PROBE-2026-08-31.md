# PP350 probe + pending runs - 2026-08-31

## 1. The probe: why did production PP16384 drop to 350?

Starts a production-equivalent server (250k ctx, ts 35,20,45, f16 K / q8_0 V,
draft+spec, mmproj, ctx-checkpoints 30), prints the fattn selector decision
and memory tables, then kills itself. No tokens generated, ~3 min.

```sh
cd /home/srcds/dev/uf3_rocm6.1_llama.cpp
LANE=pp350 TS=35,20,45 C=250000 CTK=f16 CTV=q8_0 SPEC_N_MAX=4 \
EXTRA="--ctx-checkpoints 30" PROBE=1 bash bench/lane-dflash.sh
```

Full server log: `bench/logs/lane-pp350.log`

### Read the result

Look for the `ggml_cuda_fattn: device ... AUTO:` lines:

```
... AUTO: f16 shadow 0.48 GiB, free 15.xx GiB -> f16 convert   # convert fits
... AUTO: f16 shadow 0.48 GiB, free X.xx GiB -> native         # flipped native
```

Expected verdict: native (prime suspect: `--ctx-checkpoints 30` VRAM reserve,
which the lanes never load). That explains PP16384 350 (native-class) vs the
old build's 363 (convert-class); nothing is broken.

### If it says native - the one-line remedy

Add to the env block of `2llama-start-iq6v-dflash2.sh` (line ~27):

```sh
GGML_CUDA_FATTN_PATH=force_convert
```

Expected after restart: client PP16384 back to ~363, deep fill to ~228 class,
TG 12.5-12.6. Shadow is only ~0.48 GiB, it fits alongside the checkpoints.
